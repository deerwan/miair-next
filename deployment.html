部署与配置 ​

前提:必须使用 host 网络 ​

DLNA 依赖 SSDP(1900/udp)、AirPlay 依赖 mDNS(5353/udp)组播,桥接网络下投送端无法发现音箱。因此仅支持 Linux 宿主机(macOS / Windows 的 Docker Desktop 不支持 host 网络组播)。

host 网络下容器直接绑定宿主机端口,不要写 -p 8300:8300,改端口只需调整环境变量 MIAIR_WEB_PORT。

安装方式 ​

方式一:一键安装脚本 ​

bash
curl -fsSL https://raw.githubusercontent.com/deerwan/miair-next/main/install.sh | bash

方式二:docker run ​

bash
docker run -d \
  --name miair-next \
  --network host \
  --restart unless-stopped \
  -e MIAIR_WEB_PORT=8300 \
  -v $(pwd)/data:/app/data \
  mrdeer1997/miair-next:latest

方式三:docker compose ​

bash
docker compose up -d

启动后访问 http://<宿主机IP>:8300,首次访问将引导创建管理员账号,登录后在「账号配置」中填入小米账号 / Cookie 并选择音箱。

AirPlay 2（实验性） ​

标准镜像已包含 Shairport Sync 和 NQPTP，按上述原有流程安装或更新即可，无需另装镜像。保留原有数据目录，更新后在「系统设置 → 服务设置」开启「为一个音箱启用 AirPlay 2（实验性）」并选择目标音箱、保存。其他音箱继续使用 AirPlay 1，已有协议配置会保留。参阅配置、验证和限制。

管理脚本 manage.sh ​

bash
./manage.sh start      # 启动容器
./manage.sh stop       # 停止容器
./manage.sh restart    # 重启容器
./manage.sh logs       # 查看最近日志 (logs -f 实时跟踪)
./manage.sh status     # 查看容器状态
./manage.sh update     # 拉取最新镜像并重建容器 (数据保留)
./manage.sh uninstall  # 删除容器 (数据目录保留)

可用环境变量覆盖默认约定:MIAIR_IMAGE(镜像)、MIAIR_CONTAINER(容器名)、MIAIR_DATA_DIR(数据目录)、MIAIR_WEB_PORT(Web 端口)。

镜像标签策略 ​

标签触发方式用途
edge推送到 main 分支并通过检查最新主分支镜像
latest推送到 main 或打 v*.*.* tag 并通过检查原有安装 / 更新流程默认使用的镜像
1.2.3 / 1.2打 v1.2.3 tag锁定具体版本
<short-sha>每次构建精确回滚定位

镜像由 GitHub Actions 云端构建,支持 linux/amd64、linux/arm64(涵盖 x86 主机 / NAS、树莓派 4+ 等主流部署环境)。发布前必须通过后端 / 前端检查及两种架构的标准镜像启动和 AirPlay 2 生命周期检查。合并到 main 且流水线成功后，按原有流程拉取并重建容器即可使用新镜像；运行中的容器不会自动更新。打 tag 时 CI 还会自动创建 GitHub Release,供管理后台「检查更新」检测；仅更新 main 镜像不会产生新的 Release 通知。

数据目录 ​

所有运行数据持久化在数据目录(容器内 /app/data,宿主机映射目录):

data/
├── conf/          # 引擎业务配置 (config.json / .mi.token / miair.log)
│   ├── enc.key    # config.json 敏感字段加密密钥
├── miair.db       # SQLite (管理员账号)
├── secret.key     # JWT 密钥 (首次启动随机生成)
└── spotify/       # Spotify 畅联 (可选)
    ├── bin/       # 官方 Soloist 二进制 (运行时从 Spotify CDN 下载, 不随镜像分发)
    ├── state/     # Spotify Connect 登录凭据 (配对后持久化)
    └── cache/     # 播放缓存

⚠️ 凭据存储: conf/config.json 中的小米账号密码、Cookie、飞书 Webhook、Spotify API Key 等敏感字段使用 AES-GCM 加密；conf/enc.key 必须与配置一起备份。.mi.token 仍包含明文 serviceToken，文件权限限制为 600。enc.key 与配置位于同一目录，因此整个数据目录或备份仍应妥善保护并加密存放。

DLNA 媒体缓冲的大文件会滚动写入 conf 所在的数据目录，普通播放和代理 Range 响应按块读写。缓冲总量最多 200 MiB，并根据剩余空间下调预算；请确保数据目录可写且有足够空间。

关于 MIAIR_TRUST_PROXY ​

⚠️ 只在面板确实部署于可信反向代理之后时才开启。

直连部署(客户端直接访问 8300)下若开启,登录限速会按可伪造的 X-Forwarded-For 计算,攻击者每次换一个头值即可绕过「连续失败锁定」,同时登录日志中的 IP 也会被污染。

反向代理需保证覆盖(而非追加)该头,以 Nginx 为例:

nginx
proxy_set_header X-Forwarded-For $remote_addr;

Spotify 畅联 (可选) ​

让小爱音箱作为 Spotify Connect 设备，由手机或桌面端 Spotify App 投送播放。详细使用方法、架构剖析、音量模型与故障排查请参阅专项目录：Spotify 畅联指南。

  1. 使用 Spotify Premium 账号登录 Spotify for Developers，在 Spotify Soloist API Key 页面生成专用 API Key；
  2. 在管理后台「系统设置 → Spotify 畅联」中启用、填入 API Key、选择目标音箱并保存；
  3. 打开手机 Spotify App 的设备列表，选择配置的设备名完成配对；凭据将持久化保存，重启自动恢复。

公网暴露 (安全加固) ​

默认部署面向局域网。若需从公网访问管理后台:

  • 不要直接把 8300 端口暴露到公网。登录后的 JWT 走明文 HTTP, 存在被嗅探风险;
  • 建议套一层 HTTPS 反向代理, 以 Caddy 为例 (自动签发证书):
miair.example.com {
    reverse_proxy 127.0.0.1:8300
}

Nginx 同理, /api/v1/ws 是 WebSocket, 必须配置升级头, 完整示例:

nginx
server {
    listen 443 ssl;
    server_name miair.example.com;
    # ssl_certificate / ssl_certificate_key 按实际路径填写

    location / {
        proxy_pass http://127.0.0.1:8300;
        # WebSocket 升级 (实时日志与音箱状态推送走 /api/v1/ws)
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        # 覆盖 (而非追加) 客户端 IP 头, 防伪造绕过登录限速
        proxy_set_header X-Forwarded-For $remote_addr;
        # WS 长连接需要比默认值更长的空闲超时
        proxy_read_timeout 300s;
    }
}
  • 若置于反代之后, 请设置 MIAIR_TRUST_PROXY=1, 否则登录限速与登录日志看到的都是反代 IP(全部客户端被当成同一个来源, 一人失败次数过多会连带锁住所有人); 反之, 直连部署时不要设置, 详见上文「关于 MIAIR_TRUST_PROXY」;
  • 反代只需转发 Web 管理后台。DLNA/AirPlay 的组播发现仅局域网有效, 无法也不应暴露到公网;
  • 配合防火墙限制 8300 仅本机/内网访问 (例如 ufw allow from 192.168.0.0/16 to any port 8300)。

升级 ​

bash
./manage.sh update
# 或手动: docker pull mrdeer1997/miair-next:latest && 删除旧容器后按「方式二」重建
